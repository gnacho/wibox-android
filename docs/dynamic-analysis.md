# Controlled dynamic analysis of Wibox Fermax v2.2

Date: 2026-10-31. Sheets `leaf-1.2.3` and `leaf-1.2.5`.

## 1. Executive result

Two separate attempts were made and the evidence of both is kept.

**Attempt 1:** the Android 37 ARM64 AVD did not boot on the x86_64 host. There was no installation and no traffic.

**Attempt 2:** the official Android 30 Google APIs x86_64 image did run the original APK through per-process ARM translation. The APK was installed, started cold and reached the empty main screen with no bound devices.

**Attempt 3:** a fully fictitious laboratory QR code was introduced through DocumentsUI. The online query did not reach `userFreeRegister`/`userLogin` and there was no bind. On the other hand, the updater returned HTTP 200 and a complete XML with `result=0`, which provides the first observed success request+response.

Dynamic result of attempt 2:

- Native translation confirmed: `Initialized NDK translation (aarch64), version 0.2.2`.
- One stock request observed by MITM: GET of the updater `version_check.jsp`.
- HTTPS connections from Wibox to `fermax.qvcloud.net:443` confirmed by DNS and UID.
- TCP connections from Wibox to port `1884` confirmed, with exact payload and function undecoded.
- No observed opaque session was generated, nor registration, login, OAuth, Shadow or bound device.
- There is no HTTP response from the updater: the upstream presented an expired certificate and MITM cut before receiving it.
- No new operation can leave `Unsupported`.
- Full cloud compatibility is not claimed.

## 2. Authorization and scope

The authorization allows running the original APK only on an isolated emulator, accepting the opaque registration of a test session generated by the app and capturing local traffic.

None of these actions was performed:

- Use a physical phone or its network.
- Reuse `wibox-test` to run the APK.
- Open `Add Device`, bind video intercoms or enter fictitious IDs.
- Enter the user's accounts or secrets.
- Activate `lock1`, `F1`, call, preview or any physical action.
- Modify firmware or contact duhow/cmos486 or laboratories.
- Use root, Frida, Objection or a manually installed translator.
- Relax TLS of the Kotlin client. In attempt 3 `ssl_insecure` was allowed only in the laboratory proxy to read the expired upstream, never in the client.

The terms were accepted inside the test AVD and an Android 10 informative notice was closed, steps needed to reach the stock main screen. In attempt 3 a fictitious four-field QR code was additionally authorized, never scanned from a real device, to try the opaque registration without confirming the final bind.

## 3. Official sources for attempt 2

The primary sources consulted and applied are:

1. Android Developers Blog, "Run ARM apps on the Android Emulator":
   https://android-developers.googleblog.com/2020/03/run-arm-apps-on-android-emulator.html
2. Android Emulator release notes:
   https://developer.android.com/studio/releases/emulator

The first explains that Android 11 Google APIs images run the x86 system natively and translate ARM instructions to x86 inside the app process. The technology is available in Google APIs/Play Store images and does not require root or a manual translator installation.

For network capture, the official advanced networking and console documentation was also checked. It distinguishes the QEMU PCAP from the WiFi capture through netsim and documents `-feature -WiFiPacketStream` to revert the shared network model.

## 8. Reproducible procedure

### 8.1 Image and AVD of attempt 2

```bash
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk
export ANDROID_HOME="$HOME/Android/Sdk"

"$ANDROID_HOME/cmdline-tools/latest/bin/sdkmanager" \
  'system-images;android-30;google_apis;x86_64'

printf 'no\n' | "$ANDROID_HOME/cmdline-tools/latest/bin/avdmanager" \
  create avd \
  -n wibox-stock-arm \
  -k 'system-images;android-30;google_apis;x86_64' \
  -d pixel_6
```

### 8.2 Boot and ABI check

```bash
"$ANDROID_HOME/emulator/emulator" \
  -avd wibox-stock-arm -port 5558 \
  -no-window -no-audio -no-boot-anim \
  -no-snapshot -no-snapshot-save -no-snapshot-load \
  -no-metrics -gpu swiftshader_indirect -memory 2048 \
  -tcpdump /home/nacho/temp/opencode-work/wibox-dynamic-raw/attempt2/capture.pcap
```

```bash
ADB="$ANDROID_HOME/platform-tools/adb"
"$ADB" -s emulator-5558 wait-for-device
"$ADB" -s emulator-5558 shell getprop ro.product.cpu.abilist
"$ADB" -s emulator-5558 shell getprop ro.product.cpu.abilist64
"$ADB" -s emulator-5558 shell getprop ro.dalvik.vm.isa.arm64
```

### 8.3 Stock installation and startup

```bash
"$ADB" -s emulator-5558 install --no-incremental \
  "$HOME/Descargas/wibox-fermax-v2.2/Wibox-Fermax-v2.2.apk"

"$ADB" -s emulator-5558 shell am start -W \
  -n com.fermax.wibox/com.quvii.ubell.main.view.LoadingActivity
```

Result: installation `Success`, `Status: ok`, `LaunchState: COLD`. Afterwards the terms were accepted and the Android 10 notice was closed. The pairing flow was not opened.

### 8.4 Local interception

```bash

  --set confdir=/home/nacho/temp/opencode-work/wibox-dynamic-raw/attempt2/mitm-config \
  --listen-host <loopback> --listen-port 8080 \
```

No user CA was installed and upstream validation was not disabled. The Kotlin client was not modified.

## 15. Operations that can leave `Unsupported`

**Only `app_upgrade_check`, and only for the observed contract.**

- Proven: GET method, host, port 1443, path, query keys, headers, HTTP 200, response headers and success XML schema.
- Pending: non-200 responses, provider errors, update decision semantics and strict production TLS policy.
- `unsupported_updates` contains only this operation with scope `request and HTTP 200 XML success response`.

**`discoverServices` remains `Unsupported`:**

- Proven: TCP connections to port 1884, variable destinations and online queries.
- Pending: `QvLocationManager` response, regional mapping, payload, UDP/P2P and MQTT activation.

Registration, login, OAuth, list, realtime, Shadow, media, auth routes and physical actions also remain without sufficient evidence.

## 16. Capture limits and specific blocks

### 16.1 QEMU PCAP

The PCAPs generated by `-tcpdump` cover `eth0`. Wibox uses `wlan0` for QVCloud, so those files do not contain its connections. That absence is not used as proof of inactivity.

They were kept as instrumentation diagnostics, not as request evidence.

### 16.2 Host capture

The host capture attempt failed exactly with:

```text
Attempt to create packet socket failed - CAP_NET_RAW may be required
```

No root, `sudo` or `pkexec` was used.

### 16.3 Netsim

The `-netsim-args=--pcap` form was rejected by syntax. `-netsim-args "--pcap"` booted, but the shared netsimd already existed and did not generate a new PCAP. The daemon was not restarted because it could affect `wibox-test`.

### 16.4 MITM and upstream

In attempt2, the expired upstream certificate prevented observing the updater response. In attempt3, the exception limited to the proxy allowed obtaining HTTP 200 and the complete XML. Other QVCloud connections continued direct and were not decrypted.

### 16.5 Registration and OAuth

Attempt2 did not reach pairing. Attempt3 introduced a fictitious QR and activated the online query, but did not reach `userFreeRegister`. An online state was not faked nor was the scope widened to obtain a session.
